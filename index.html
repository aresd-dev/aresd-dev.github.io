Destaque

Zone

Chamadas de voz, chat e um escritório virtual 2D para equipes pequenas

O problema Eu e dois amigos queríamos conversar por texto e voz sem depender de serviços grandes. Virou um sistema em tempo real em uso por três pessoas, no navegador e em app Windows, com um escritório virtual 2D incluso.

  • Separei responsabilidades em duas linguagens, com a regra “uma regra, um dono”: Python (FastAPI) decide contas, permissões e persistência no PostgreSQL; Go cuida de WebSocket, presença e sinalização; o cliente só envia intenções, nunca estado final.
  • Projetei sessões com refresh token rotativo em cookie HttpOnly: só o hash fica no banco e a família inteira de tokens é revogada se um token antigo for reutilizado.
  • Eliminei sinais WebRTC atrasados que religavam áudio já fechado, usando gerações e IDs por sessão, contexto e transmissão: o que é antigo é descartado.
  • Mantive a infraestrutura proporcional: um único serviço Docker multi-stage no Render, mídia P2P com TURN da Cloudflare e sem Redis, filas ou servidor de mídia, porque para três pessoas não se justificam.
  • Verifiquei com mais de 2.800 testes automatizados (Go, Python, Vitest e fluxos reais no navegador), rodando a regressão inteira a cada etapa antes de avançar.

Arquitetura Navegador ou app Windows → gateway Go (site, /api, WebSocket) → API Python (FastAPI) → PostgreSQL; o escritório é um módulo Go com o mundo autoritativo, e os dois módulos só se falam por contrato HTTP/WebSocket.

~32 mil linhas de código · ~40 mil linhas de testes · 2.800+ testes · 3 pessoas usando

Postador

Agende uma vez, publique em todas as redes

O problema Cada rede social tem as suas regras e cuidar de várias contas vira trabalho repetitivo. O Postador agenda e publica em LinkedIn, Instagram, YouTube, TikTok e X usando só as APIs oficiais, num .exe para Windows. Começou como um script em Python e foi reescrito do zero.

  • Integrei 5 APIs oficiais atrás de uma interface comum (validate, publish, OAuth): uma classe por rede, então adicionar uma rede nova é escrever uma classe.
  • Resolvi o redirect HTTPS exigido pelo OAuth num app local com uma página-ponte estática no GitHub Pages que repassa code e state, com state de uso único e PKCE.
  • Garanti que nunca publica duas vezes: a seleção do agendador é uma função pura, o claim no SQLite é atômico e, se o app cai no meio do envio, o post vai para “conferir” em vez de repetir sozinho.
  • Implementei retentativas após 1, 5 e 15 min só para erros temporários, recuperação de posts perdidos com o PC desligado e upload em partes com retomada em cada rede.
  • Protegi tokens com Fernet, o acesso remoto com scrypt e sessão assinada, e a interface com limite de tentativas e checagem de origem (CSRF) e de Host (DNS rebinding).
  • Cobri tudo com 123 testes em pytest sem nenhuma chamada real de rede: o HTTP de cada rede é simulado com responses.

Arquitetura Interface FastAPI + Jinja2 → serviço de posts com validação por rede → SQLite com tokens criptografados; agendador em thread → publishers (uma classe por rede) → APIs oficiais.

~4.500 linhas de Python · 123 testes · 5 redes com várias contas cada

Shiori

Da folha do caderno para o Obsidian, com IA local

O problema Anotações à mão ficam esquecidas no papel, e OCR na nuvem expõe dados pessoais. O Shiori lê fotos de páginas com um modelo local (Ollama), separa os assuntos e só publica no vault do Obsidian depois da revisão.

  • Fiz o modelo classificar e o código decidir: a página é dividida de forma determinística, a IA diz só assunto e categoria de cada bloco, e as regras de junção e validação ficam no código.
  • Medi em 31 fotos reais com gabarito: a leitura concluída subiu de 9/31 para 28/31 ao trocar JSON por texto puro com penalidade de repetição, e as fronteiras de assunto de 9/30 para 22/30.
  • Cada clique vira uma tarefa persistente numa fila SQLite idempotente com worker único: repetir o clique não duplica e um resultado antigo nunca sobrescreve uma edição mais nova.
  • Fiz a publicação ser transacional: manifesto gravado antes de qualquer arquivo, hardlink exclusivo que nunca sobrescreve, troca atômica e desfazer que confere hashes e recusa a operação se o usuário editou depois.
  • Corrigi um bug real (uma nota saiu com título e resumo de outra página, porque a memória enviava notas inteiras como exemplo) e deixei um teste de regressão; também bloqueei SSRF no verificador web e validei os caminhos do vault.
  • Cobri com 160 testes em pytest, com o HTTP do Ollama, do Gemini e da pesquisa simulado por httpx.MockTransport e o painel testado com streamlit.testing.

Arquitetura Painel Streamlit → fila SQLite de tarefas idempotentes → worker único → segmentação + tarefas de IA (Ollama local) → publicador com manifesto e hashes → vault do Obsidian.

~3.200 linhas de Python · 160 testes · 31 fotos reais medidas

Washi

Mesa de trabalho digital local-first: hábitos, kanban, notas e um quadro infinito

O problema Eu queria um único espaço para hábitos, projetos e rabiscos, sem guardar meus dados na nuvem de alguém. Os dados do Washi ficam em arquivos comuns (Markdown, JSON) no próprio computador.

  • Separei um núcleo Python/FastAPI, que guarda as regras de negócio e o acesso a disco, de uma interface React que só desenha e envia intenções, ligados por um canal local autenticado e isolado da rede.
  • Garanti a integridade dos dados com escrita atômica, registro de operações, recuperação de arquivo truncado após queda de energia e backups automáticos com rotação.
  • Implementei um reconhecedor geométrico de gestos que decide se o traço sobre um quadradinho é ✓, ✗ ou rabisco, com tolerância para grades apertadas.
  • Fiz a interface otimista: mover, desenhar e marcar respondem na hora, o disco confirma em segundo plano e há desfazer (Ctrl+Z).
  • Cobri o núcleo com 111 testes (tipagem estrita e lint) e a interface com 32 verificações em navegador real, que acharam falhas de interação que todos os testes unitários deixavam passar.

Arquitetura Interface React + TypeScript → canal local autenticado → núcleo Python/FastAPI → vault no disco (Markdown · JSON · JSONL); um shell Electron inicia e vigia o núcleo.

111 testes no núcleo · 32 verificações em navegador real

Como eu trabalho

O mesmo ciclo em todos os projetos acima.

  • Em fatias pequenasImplemento a menor parte que entrega o comportamento, testo isolado, integro e rodo a regressão antes de avançar.
  • Bug vira testeQuando viável, o teste falha antes da correção e passa depois, e fica na suíte.
  • Teste não se enfraqueceNunca apago nem pulo um teste só para ficar verde: se o requisito mudou, atualizo e registro o motivo.
  • Relato com precisãoSeparo o que está implementado, testado e validado em uso real, e digo o que ainda depende do ambiente real.
